# immich

## Mac Studio 向け Docker Compose 構成

Mac Studio 上で Immich を動かすための最小構成。保存先はハイブリッド構成。

### ストレージ構成

- **内蔵 SSD**: PostgreSQL データ、一時アップロード領域、サムネイル、プロフィールデータ、エンコード済み動画キャッシュ、バックアップ、ML キャッシュ
- **外付け HDD**: 写真・動画のオリジナルデータ

### 同梱ファイル

- `.env.example`: `.env` のひな形
- `docker-compose.yml`: SSD と外付け HDD を分離したハイブリッドマウント構成
- `immich-cleaner/`: Smart Search で低重要度候補を確認する追加 UI

### 前提

- 公式手順: <https://docs.immich.app/install/docker-compose/>
- このリポジトリには `docker-compose.yml` と `.env.example` を同梱
- そのため、公式手順の「必要ファイルのダウンロード」は不要
- この README の対象は、クローン後のローカル調整と起動手順

### セットアップ

- クローン直後に tool と Git hook をセットアップする

  ```bash
  mise install
  mise run hooks-install
  ```

- hook 設定や secret scan を手元で確認したい場合は以下を実行する

  ```bash
  mise run hooks-validate
  mise run hooks-run
  ```

- pre-push hook を個別に確認したい場合

  ```bash
  pre-commit run gitleaks-pre-push --hook-stage pre-push
  ```

- [こちらを参照](docs/setup.md): `.env` の調整から起動まで

### .env

#### 外付け HDD ・内蔵 SSD のどちらに保存するかの判断基準

##### 内蔵SSDに絶対に置くべきデータ（速度・即時性重視）

###### データベース本体（Postgres / `DB_DATA_LOCATION`）

- **データ容量**: **小**（写真が数万枚あっても数GB〜十数GB程度）
- **読み書き頻度**: **極めて高い**（アプリを開く、スクロールする、検索するたびに数千・数万回の細かいアクセスが発生）
- **即時性**: **極めて高い**（ここがHDDだと、アプリ全体の動作が致命的に重くなります）
- 📌 **結論: 内蔵SSD（必須）**

###### サムネイル (`thumbs/`)

- **データ容量**: **中〜大**（写真の枚数によりますが、数十GB〜100GB超になることも）
- **読み書き頻度**: **高い**（タイムラインをスクロールする際、大量の小さな画像ファイルを一瞬で読み込みます）
- **即時性**: **高い**（スクロールした時に、画像がパッパッと遅延なく表示されるために必要）
- 📌 **結論: 内蔵SSD（強く推奨）**
- *補足*: HDDでこれをやると「カリカリカリ…」とヘッドが激しく動き続け、HDDの寿命を縮める大きな原因になります。また、表示も非常に遅くなります。

##### 外付けHDDへ逃がしていいデータ（容量重視）

###### オリジナルデータ（`library/`）

- **データ容量**: **極めて大きい**（全体の80%〜90%以上を占める主役）
- **読み書き頻度**: **低い〜中程度**（新しくアップロードする時と、写真をタップして「拡大表示」したり「動画を再生」したりする時だけ）
- **即時性**: **低い**（写真をタップしてからオリジナルが表示されるまでに、1秒弱のタイムラグがあっても実用上ストレスは少ない）
- 📌 **結論: 外付けHDD（最適）**

###### トランスコード済みの動画 (`encoded-video/`)

- **データ容量**: **大**（動画が多い環境ではかなり容量を食います）
- **読み書き頻度**: **低い**（スマホなどでその動画を再生する時だけ読み込まれます）
- **即時性**: **中程度**（再生開始までに1〜2秒待っても許容範囲内）
- 📌 **結論: 外付けHDD（推奨）**

###### データベースのバックアップ（`backups/`）

- **データ容量**: **小〜中**（世代管理すると多少増えますが、テキストデータなので軽め）
- **読み書き頻度**: **極めて低い**（毎日深夜の自動バックアップ時に1回書き込むだけ。読み込みは復元時のみ）
- **即時性**: **不要**
- 📌 **結論: 外付けHDD（最適、むしろ安全のため別ドライブにするべき）**

---

##### 三基準による分類まとめ表

| データ種別 | 容量 | 読み書き頻度 | 即時性 | 推奨配置 | HDDへの影響 |
| --- | --- | --- | --- | --- | --- |
| ① DB本体 | 小 🟢 | 極高 🔴 | 極高 🔴 | 内蔵SSD | HDDだと寿命・速度ともに最悪 |
| ② サムネイル | 中〜大 🟡 | 高 🔴 | 高 🔴 | 内蔵SSD | HDDだとシーク多発で消耗大 |
| ③ オリジナル | 極大 🔴 | 低〜中 🟢 | 低 🟢 | 外付けHDD | 連続書き込み/読み込みなので負担小 |
| ④ 変換済動画 | 大 🔴 | 低 🟢 | 中 🟡 | 外付けHDD | 使用時のみなので負担小 |
| ⑤ DBバックアップ | 小〜中 🟢 | 極低 🟢 | 不要 🟢 | 外付けHDD | 1日1回書き込むだけなので負担小 |
