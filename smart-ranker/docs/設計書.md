## Immichパーソナル・重要度判定システム 設計書

### 1. システム概要

Immichの既存アセットを活用し、ユーザー固有の嗜好を学習するAI（Scoring Engine）の構築。PoCでは、アセット状態やPeopleは Immich API を主経路とし、CLIP特徴量は Immich DB の read-only 参照を併用する。軽量な学習モデルにより、個人の「残したい価値観」を数値化し、画像・動画の自動整理を実現する。

---

### 2. コンポーネント構成

* **Data Source (Immich API + DB read-only):** Immich API からアセットメタデータ、状態、People メタデータを取得し、Immich DB の read-only 接続から CLIP特徴量（Embedding）を取得する。
* **Event Collector:** Immich APIを定期ポーリングし、trash / restore、削除候補からの手動除外の差分を取得する。PoC では差分収集カーソルと Weak Positive のフィードバック履歴を Smart Ranker 側へ保存する。
* **Training Engine:** 現在のアセット状態とフィードバック履歴を用いて教師ラベルを再構成し、学習処理を行う。
* **Inference Engine:** 未分類アセットに対する重要度スコアの算出。
* **Action Controller:** スコアに基づくタグ付け、アルバム移動、ゴミ箱転送の実行。

---

### 3. データ定義と重み付けアルゴリズム

#### 学習データの定義

| クラス | 抽出条件（Immich上） | 教師ラベル |
| --- | --- | --- |
| **重要度：高 (Positive)** | お気に入り、かつ trash ではない（isFavorite: true, isTrashed: false） | 1 |
| **重要度：準高 (Weak Positive)** | AI が追加した「削除候補」からユーザーが手動で除外したアセット | 1 |
| **重要度：低 (Strong Negative)** | trash に入ったアセット（isTrashed: true） | 0 |
| **学習対象外 (Unlabeled)** | 通常アセット（isFavorite: false, isTrashed: false, visibility: timeline） | 学習に使わない |

#### ラベル付けルール

* **Archived:** `visibility: archive` のアセットは学習に使用しない。
* **Delete タグ:** 使用しない。Immich ネイティブ状態のみを教師信号に使う。
* **Weak Positive の確定タイミング:** Smart Ranker が追加した「削除候補」からユーザーが手動で除外した時点で確定する。
* **Weak Positive の保持方法:** 手動除外時点のスコア、カテゴリ、必要メタデータを Smart Ranker 側の `feedback_event` へ追記型で保存する。PoC では Positive と同じラベル 1 を付与し、学習時のサンプル重みで弱める。
* **Strong Negative の確定タイミング:** trash 入り時点で確定する。
* **Strong Negative の保持方法:** PoC では現在の `isTrashed: true` を教師ラベル 0 として扱う。permanently delete 後の復元や履歴再構成は行わない。
* **Restore 時の扱い:** PoC では restore 済みアセットを Strong Negative として保持しない。現在状態の再取得結果を正とする。
* **Unlabeled の扱い:** 通常アセットは推論対象とするが、PoC の学習集合には含めない。
* **衝突ルール:** `trash > archive > favorite > weak positive > unlabeled` の順に優先する。`isTrashed: true` を最優先し、trash でなければ `visibility: archive` は学習除外、それ以外で `isFavorite: true` を Positive、手動除外イベントがあれば Weak Positive とする。
* **運用前提:** Immich 側の trash を有効化して運用する。

#### 採用アルゴリズム

* **特徴量:** CLIP（ViT-L/14等）から抽出された多次元ベクトル。
* **モデル:** Logistic Regression（ロジスティック回帰）の二値分類。
* *選定理由:* PoC では Positive / Negative の教師信号が明確であり、計算負荷の低さ、および特徴量ごとの重み（係数）の可視化の容易さに優れるため。

* **出力:** Positive クラスに属する確率としての 0.0〜1.0 の連続値（重要度スコア）。

#### 初期ラベル構成

* **基本6ラベル:** 風景、人物、書類、スクリーンショット、ペット、その他。
* **特別2ラベル:** 家族、我が子。
* **モデル構成:** 基本6ラベル、特別2ラベルに加え、全アセット共通の汎用モデルを持つ。
* **ラベルの性質:** ラベルは排他的にしない。1つのアセットに複数ラベルを付与できる。
* **特別2ラベルの位置づけ:** 「家族」「我が子」は「人物」を置き換えず、人物系の追加ラベルとして扱う。
* **人物系ラベルグループ:** 「人物」「家族」「我が子」は同時付与を許可するが、学習と推論で有効化する教師モデルは常に1つだけとする。
* **人物系ラベルグループの優先順位:** `我が子 > 家族 > 人物`。
* **PoC のラベル付与方針:** 人物系は People メタデータで決定的に付与する。書類、スクリーンショットは OCR、ファイル名、パス、手動タグなどの機械的ルールを優先する。風景、ペットは smart search の結果を弱ラベルとして使う。その他はフォールバックとして扱う。
* **Smart Search の位置づけ:** `search/smart` はカテゴリ候補を生成する補助信号であり、確定ラベルではなく弱ラベルとして扱う。
* **各モデルの判定軸:** いずれのラベルでも、CLIP特徴量と通常メタデータを用いて重要度を判定する。
* **総合スコアの作り方:** 汎用モデルと、人物系では優先順位で選ばれた1モデル、それ以外の該当ラベルモデル群のスコアを保持し、v1ではその最大値を総合スコアとして採用する。

#### 特別ラベルの判定ルール

1. 「家族」「我が子」は、Immich上で名前付け済みのPersonを前提とする。
1. 初期設定時に人名からPersonを検索し、内部ではPerson IDの集合として保持する。
1. 人物を含むアセットには、People メタデータに応じて「人物」に加え、「家族」または「我が子」を追加付与する。
1. `people` に我が子のPerson IDが含まれる場合は、「人物」と「我が子」を付与する。
1. 我が子には一致せず、家族のPerson IDが含まれる場合は、「人物」と「家族」を付与する。
1. どちらにも一致しない人物アセットは、「人物」のみを付与する。
1. 顔が未検出、未命名、または人物が主対象でないアセットは、基本6ラベルの該当候補のみを付与する。
1. 人物系ラベルが複数付与された場合でも、有効化する教師モデルは `我が子 > 家族 > 人物` の順で最上位の1つに限定する。
1. ラベル付与後の重要度判定は、汎用モデルと、人物系では最上位1モデル、それ以外の該当ラベル専用モデルが行う。

* **動画への適用:** 動画も対象とする。ただし顔認識はImmichが生成したpreview image上の検出結果に依存する。

#### 非人物系ラベルの判定ルール

1. 「書類」「スクリーンショット」は、OCR テキスト、ファイル名、`originalPath`、手動タグ、拡張子などの機械的ルールを優先して付与する。
1. 「風景」「ペット」は、対象期間または推論対象バッチに絞った `search/smart` をカテゴリごとに実行し、その結果集合を弱ラベルとして扱う。
1. `search/smart` のクエリ語はカテゴリごとに複数持てるようにし、設定値として管理する。たとえば「風景」は `landscape`、`nature`、`風景`、`自然` などを候補とする。
1. `search/smart` で取得できたアセットは、そのカテゴリの候補ラベルへ追加する。ただし確定ラベルではなく、モデル選択と優先順位付けに使う弱ラベルとする。
1. どの機械的ルールにも `search/smart` にも一致しないアセットは、「その他」の候補とする。
1. 複数の非人物系ラベルが同時に成立してよい。

#### PoC 実装方針

* **取得経路:** アセット状態、People、操作系は Immich API を使い、CLIP特徴量のみを Immich DB の read-only 接続から取得する。
* **差分収集:** `updatedAfter` と `trashedAfter` は Smart Ranker 側で収集カーソルを保持し、run 完了時にのみ更新する。
* **API 追加方針:** backend API は必要になった機能から段階的に追加する。
* **API 最低限ルール:** ジョブ実行 API は冪等とし、手動実行 API は `jobRunId` を返す。一覧 API は `page` または `nextPage` のどちらかに統一する。

### 4. 処理プロセス

#### ステップ1：データ収集（Fetch）

1. Immich API経由で全アセットの UUID、`isFavorite`、`isTrashed`、`visibility`、`people` メタデータ、OCR テキスト、ファイル名、パス、手動タグなどの通常メタデータを取得し、Immich DB の read-only 接続から対応する CLIP ベクトルを取得する。
1. `POST /search/metadata` などの API フィルタで `updatedAfter` と `trashedAfter` を使い、trash / restore の差分を定期取得する。
1. 差分収集カーソルは Smart Ranker 側で保持し、run が成功した時点でのみ更新する。
1. Smart Ranker が管理する「削除候補」アルバムの所属差分、または GUI 上の手動除外操作を取得し、対応するアセットを Weak Positive のフィードバックイベントとして保存する。
1. `/people` または `/search/person` を用いて、「家族」「我が子」に対応するPersonを解決し、Person IDを設定値として保持する。
1. カテゴリ定義ごとに、対象期間または推論対象バッチへ `search/smart` を実行し、風景、ペットなどの弱ラベル候補集合を生成する。
1. ベクトルデータと人物メタデータ、OCR/ファイルメタデータ、smart search の弱ラベル候補を学習用マトリックスに変換する。

#### ステップ2：モデル学習（Train/Update）

1. 現在のアセット状態とフィードバック履歴から教師ラベルを再構成する。
1. `trash > archive > favorite > weak positive > unlabeled` の順でラベルを確定し、archive と unlabeled は学習集合から除外する。
1. 各アセットについて、People メタデータ、OCR、ファイル名、パス、手動タグなどの通常メタデータと、smart search の弱ラベル候補から候補ラベル集合を生成する。
1. 書類、スクリーンショットは機械的ルールを優先し、風景、ペットは smart search の弱ラベルを候補へ加える。
1. 人物系ラベルが複数ある場合は、`我が子 > 家族 > 人物` の順で有効ラベルを1つに絞る。
1. 1アセットを、有効化された人物系ラベルと、それ以外の該当ラベルの学習集合へ複写し、ラベル別の二値分類器を訓練する。
1. ラベル別モデルとは別に、全ラベル共通の学習集合を対象とした汎用モデルも訓練する。
1. 「ユーザーが何を重視しているか（色合い、被写体、構図等）」をモデル内部の重みに集約。
1. 学習済みモデル、Person ID 設定、ラベル定義をローカル（`.pkl`、`.json`等）に保存。

#### ステップ3：推論および自動処理（Inference/Action）

1. 新着アセットを検知し、`isTrashed: false` かつ `visibility: timeline` のアセットを推論対象とする。
1. People メタデータ、OCR、ファイル名、パス、手動タグなどの通常メタデータと、smart search の弱ラベル候補から候補ラベル集合を生成する。
1. 書類、スクリーンショットは機械的ルールを優先し、風景、ペットは smart search の弱ラベルを候補へ加える。
1. 人物系ラベルが複数ある場合は、`我が子 > 家族 > 人物` の順で適用モデルを1つに絞る。
1. 汎用モデルと、人物系では選択された1モデル、それ以外の該当ラベル専用モデルが、CLIP特徴量と通常メタデータを用いてスコアを算出する。
1. ラベル別スコアを保持し、総合スコアには最大値を採用する。
1. 設定された閾値（例：Score < 0.2）に基づき、以下の処理を実行。

* **Reviewタグの付与:** 確認用アルバムへの自動追加。
* **メタデータ更新:** 説明欄にスコアを記載。

---

### 5. AIを「育てる」ためのフィードバックループ

1. **AIの判定:** スコアの低いアセットを「削除候補」アルバムへ移動。
1. **ユーザーの確定操作:** 保持したいアセットは「お気に入り」へ、または「削除候補」から手動で除外する。不要なアセットは Immich の trash へ移動。
1. **イベント記録:** PoC では「削除候補」からの手動除外のみを Weak Positive として `feedback_event` に記録する。Strong Negative は現在の `isTrashed: true` を直接参照する。
1. **再学習の実行:** 定期的なバッチ処理により、現在のアセット状態と有効なフィードバック履歴から教師データを再構成し、モデルを更新。

* **結果:** 使うほどにユーザーの「捨てられない基準」を反映した高精度なモデルへと進化。

---

### 6. 実装環境・ツール

* **言語:** Python 3.10+
* **主要ライブラリ:** `scikit-learn` による二値分類モデル構築と学習、`requests` によるImmich APIとの通信、`numpy/pandas` によるベクトル演算とデータ管理、Postgres クライアントによる read-only DB 参照。
* **補助ストレージ:** Weak Positive を含むフィードバック履歴と差分収集カーソルは Smart Ranker 側の軽量ストレージ（例: SQLite）に保持。

* **実行形態:** Dockerコンテナ（Immichと同一ネットワーク内）またはcronによる定期実行スクリプト。

### 7. 今後の拡張性

* **マルチモデル化:** 基本6ラベル（風景、人物、書類、スクリーンショット、ペット、その他）と特別2ラベル（家族、我が子）を排他的にせず併用する。1つのアセットに複数ラベルを付与するが、人物系は `我が子 > 家族 > 人物` の順で最上位の1モデルだけを有効化し、それ以外の該当ラベルモデルと汎用モデルを併用する。たとえば家族旅行は「風景 + 人物 + 家族」のラベルを持つが、人物系モデルは「家族」のみを使う。レシートのスクリーンショットは「書類 + スクリーンショット」として扱う。将来的には「家族イベント」「集合写真」「旅行」「食事」などの派生ラベルへ拡張する。
* **重複除外の統合:** CLIPベクトルの近傍探索による、類似した連写画像からの「ベストショット」選定機能。

構築の第一段階として、API経由での Favorite アセット取得、DB read-only 経由での CLIP ベクトル取得、差分収集カーソルの確立を推奨。
