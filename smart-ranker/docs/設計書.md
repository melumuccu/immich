## Immichパーソナル・重要度判定システム 設計書

### 1. システム概要

Immich の既存アセットを活用し、ユーザー固有の嗜好を学習する AI を構築する。PoC では、アセット状態や People は Immich API を主経路とし、CLIP 特徴量は Immich DB の read-only 参照を併用する。軽量な学習モデルにより、個人の「残したい価値観」を数値化し、画像と動画の自動整理を行う。

v2 では `collect` と `train` を単独 job として分けず、学習信号の同期とモデル更新を 1 回で完了する統合 job `learn` を中心に据える。`score` は全 asset を対象に最新モデルで点数化し、GUI は全件をスコア順で表示する。`apply` は GUI で保持する削除閾値以下の asset を Review Album へ追加する。ユーザーは Review Album 上で不要なら手動 trash、残すなら手動でアルバムから除外し、その結果を次回の `learn` に反映させる。

---

### 2. コンポーネント構成

* **Data Source (Immich API + DB read-only):** Immich API からアセットメタデータ、状態、People メタデータを取得し、Immich DB の read-only 接続から CLIP 特徴量を取得する。
* **Training Signal Collector:** 現在 favorite の asset 群と現在 trash の asset 群だけを同期し、Smart Ranker DB の `favorite_signal` と `trash_signal` を更新する。favorite 解除や restore を検出した場合も行を消さず、終了時刻を付けて保持する。
* **Training Engine:** `favorite_signal` と `trash_signal` を用いて教師ラベルを再構成し、学習処理を行う。Review Album に送っただけの asset は学習に使わず、ユーザーが実際に手動 trash した時点で negative として取り込む。
* **Inference Engine:** 全 asset を対象に重要度スコアを算出し、GUI 表示用の score snapshot を保存する。
* **Score Review GUI:** 全 asset をスコア順で表示し、削除閾値を操作する。人手での確認と閾値調整の起点にする。
* **Action Controller:** 閾値以下の asset を Review Album へ追加し、`action_execution_log` と `apply_exclusion_asset` を更新する。`apply_exclusion_asset` は重複 apply の抑止に使う。

---

### 3. データ定義と重み付けアルゴリズム

#### 学習データの定義

| クラス | 抽出条件 | Smart Ranker 側の保持 | 教師ラベル |
| --- | --- | --- | --- |
| **重要度: 高 (Positive)** | ユーザーが favorite した asset | `favorite_signal` に保持。favorite 解除後も保持 | 1 |
| **重要度: 低 (Strong Negative)** | ユーザーが trash へ入れた asset | `trash_signal` に保持。restore 後も保持 | 0 |
| **レビュー待ち (Review Album)** | `apply` が閾値以下として Review Album へ追加した asset | `apply_exclusion_asset` に保持。重複 apply を防ぐ | 学習に使わない |
| **学習対象外 (Unlabeled)** | 上記の手動 signal を持たない asset | score 対象としてのみ扱う | 学習に使わない |

#### ラベル付けルール

* **signal の分離保持:** favorite と trash は別テーブルで保持する。片方の状態変化が他方の履歴を消さない。
* **favorite 解除時の扱い:** favorite 解除を検出した場合は `favorite_signal.cleared_at` を更新するが、学習用 signal は残す。
* **restore 時の扱い:** restore を検出した場合は `trash_signal.restored_at` を更新するが、学習用 signal は残す。
* **教師ラベルの再構成:** 1 asset に favorite と trash の両方の履歴がある場合は、直近の手動 signal を優先する。同時刻衝突は `trash > favorite` を優先する。
* **Review Album の扱い:** `apply` で Review Album へ追加した asset は `apply_exclusion_asset` に載せ、同じ asset の重複 apply を防ぐ。`learn` は実際に手動 trash された場合だけ `trash_signal` として再収集する。
* **score の対象:** `score` は asset 全件を対象にする。すでに trash に入っている asset も score snapshot へ残す。
* **apply の対象:** `apply` は最新 score snapshot のうち、閾値以下、未保護、未 trash の asset を対象にする。

#### 採用アルゴリズム

* **特徴量:** CLIP（ViT-L/14 等）から抽出された多次元ベクトル。
* **モデル:** Logistic Regression の二値分類。
* **選定理由:** PoC では Positive / Negative の教師信号が明確であり、計算負荷の低さと重みの説明可能性に優れるため。
* **出力:** Positive クラスに属する確率としての 0.0〜1.0 の連続値。

#### 初期ラベル構成

* **基本 6 ラベル:** 風景、人物、書類、スクリーンショット、ペット、その他。
* **特別 2 ラベル:** 家族、我が子。
* **モデル構成:** 基本 6 ラベル、特別 2 ラベルに加え、全 asset 共通の汎用モデルを持つ。
* **ラベルの性質:** ラベルは排他的にしない。1 つの asset に複数ラベルを付与できる。
* **特別 2 ラベルの位置づけ:** 「家族」「我が子」は「人物」を置き換えず、人物系の追加ラベルとして扱う。
* **人物系ラベルグループ:** 「人物」「家族」「我が子」は同時付与を許可するが、学習と推論で有効化する教師モデルは常に 1 つだけとする。
* **人物系ラベルグループの優先順位:** `我が子 > 家族 > 人物`。
* **PoC のラベル付与方針:** 人物系は People メタデータで決定的に付与する。書類、スクリーンショットは OCR、ファイル名、パス、手動タグなどの機械的ルールを優先する。風景、ペットは smart search の結果を弱ラベルとして使う。その他はフォールバックとして扱う。
* **Smart Search の位置づけ:** `search/smart` はカテゴリ候補を生成する補助信号であり、確定ラベルではなく弱ラベルとして扱う。
* **各モデルの判定軸:** いずれのラベルでも、CLIP 特徴量と通常メタデータを用いて重要度を判定する。
* **総合スコアの作り方:** 汎用モデルと、人物系では優先順位で選ばれた 1 モデル、それ以外の該当ラベルモデル群のスコアを保持し、v2 でもその最大値を総合スコアとして採用する。

#### 特別ラベルの判定ルール

1. 「家族」「我が子」は、Immich 上で名前付け済みの Person を前提とする。
1. 初期設定時に人名から Person を検索し、内部では Person ID の集合として保持する。
1. 人物を含む asset には、People メタデータに応じて「人物」に加え、「家族」または「我が子」を追加付与する。
1. `people` に我が子の Person ID が含まれる場合は、「人物」と「我が子」を付与する。
1. 我が子には一致せず、家族の Person ID が含まれる場合は、「人物」と「家族」を付与する。
1. どちらにも一致しない人物 asset は、「人物」のみを付与する。
1. 顔が未検出、未命名、または人物が主対象でない asset は、基本 6 ラベルの該当候補のみを付与する。
1. 人物系ラベルが複数付与された場合でも、有効化する教師モデルは `我が子 > 家族 > 人物` の順で最上位の 1 つに限定する。
1. ラベル付与後の重要度判定は、汎用モデルと、人物系では最上位 1 モデル、それ以外の該当ラベル専用モデルが行う。

* **動画への適用:** 動画も対象とする。ただし顔認識は Immich が生成した preview image 上の検出結果に依存する。

#### 非人物系ラベルの判定ルール

1. 「書類」「スクリーンショット」は、OCR テキスト、ファイル名、`originalPath`、手動タグ、拡張子などの機械的ルールを優先して付与する。
1. 「風景」「ペット」は、対象期間または推論対象バッチに絞った `search/smart` をカテゴリごとに実行し、その結果集合を弱ラベルとして扱う。
1. `search/smart` のクエリ語はカテゴリごとに複数持てるようにし、設定値として管理する。たとえば「風景」は `landscape`、`nature`、`風景`、`自然` などを候補とする。
1. `search/smart` で取得できた asset は、そのカテゴリの候補ラベルへ追加する。ただし確定ラベルではなく、モデル選択と優先順位付けに使う弱ラベルとする。
1. どの機械的ルールにも `search/smart` にも一致しない asset は、「その他」の候補とする。
1. 複数の非人物系ラベルが同時に成立してよい。

#### PoC 実装方針

* **取得経路:** asset 状態、People、操作系は Immich API を使い、CLIP 特徴量のみを Immich DB の read-only 接続から取得する。
* **learn の収集対象:** 現在 favorite の asset と現在 trash の asset だけを同期する。asset 全件の collect は行わない。
* **履歴保持:** `favorite_signal` と `trash_signal` は signal の終了後も保持し、手動操作の履歴を教師データへ再利用できるようにする。
* **Review Album 抑止台帳:** `apply` 成功時に `apply_exclusion_asset` を更新し、同じ asset の重複 apply を避ける。
* **score snapshot:** `score` は asset 全件を score し、GUI 表示用の snapshot を run 単位で保存する。
* **GUI 最低限ルール:** GUI は score 一覧を昇順で表示し、削除閾値を即時更新できる。`apply` は常に GUI 上の最新閾値を使い、閾値以下を Review Album へ送る。

### 4. 処理プロセス

#### ステップ 1: 学習信号同期とモデル更新 (`learn`)

1. Immich API 経由で現在 favorite の asset 群と現在 trash の asset 群を取得する。
1. `favorite_signal` と `trash_signal` を別々に upsert し、対象から外れた asset には `cleared_at` または `restored_at` を設定する。
1. `apply_exclusion_asset` に載っている asset は trash 側の同期対象から除外する。
1. CLIP 特徴量、People メタデータ、OCR テキスト、ファイル名、パス、手動タグ、smart search の弱ラベル候補を特徴量行列へ変換する。
1. asset ごとに favorite / trash の直近手動 signal を比較し、教師ラベルを再構成する。
1. 汎用モデルとラベル別モデルを学習し、モデル本体と設定 snapshot を保存する。

#### ステップ 2: 全件スコアリング (`score`)

1. Immich API と Immich DB から asset 全件のメタデータと CLIP 特徴量を取得する。
1. People、OCR、ファイル名、パス、手動タグ、smart search の弱ラベル候補から候補ラベル集合を生成する。
1. 汎用モデルとラベル別モデルで score を算出する。
1. ラベル別スコアと総合スコアを `score_run` / `score_result` へ保存する。
1. GUI は最新の `score_run` を読み、全 asset を総合スコア順で表示する。
1. GUI 上で削除閾値を更新し、次の `apply` に使う。

#### ステップ 3: 閾値適用 (`apply`)

1. 最新 `score_run` と GUI 上の削除閾値を読む。
1. 閾値以下、未保護、未 trash の asset を抽出する。
1. Immich API で対象 asset を Review Album へ追加する。
1. 実行結果を `action_execution_log` に保存する。
1. Review Album へ追加した asset を `apply_exclusion_asset` に登録し、同じ asset の重複 apply を防ぐ。

---

### 5. AI を育てるためのフィードバックループ

1. **ユーザーの手動操作:** 保持したい asset は favorite、不要な asset は Immich の trash へ入れる。
1. **signal の保持:** `learn` は favorite と trash を別々に保持し、favorite 解除や restore の後も学習 signal として残す。
1. **全件スコア確認:** `score` が全 asset を点数化し、GUI がスコア順一覧を提示する。
1. **閾値の調整:** ユーザーが GUI で削除閾値を上下させ、どこから Review Album へ送るかを決める。
1. **Review Album 運用:** `apply` が閾値以下の asset を Review Album へ追加する。ユーザーは不要なら手動 trash、残すなら手動でアルバムから除外する。

* **結果:** 手動 favorite / manual trash だけを教師信号としつつ、Review Album を経由した人手確認で低スコア候補を運用できる。

---

### 6. 実装環境・ツール

* **言語:** Python 3.10+
* **主要ライブラリ:** `scikit-learn` による二値分類モデル構築と学習、`requests` による Immich API 通信、`numpy/pandas` によるベクトル演算とデータ管理、Postgres クライアントによる read-only DB 参照。
* **補助ストレージ:** favorite / trash signal、score snapshot、閾値設定、Review Album 送付台帳としての `apply_exclusion_asset`、ジョブ実行履歴を Smart Ranker 側の軽量ストレージに保持する。
* **実行形態:** Docker コンテナ、または cron / scheduler からの定期実行。

---

### 7. 今後の拡張性

* **再学習の高度化:** signal の recency weight、favorite 回数、restore 後の再 favorite などを重みに反映する。
* **スコア確認 UI の強化:** score 一覧の絞り込み、カテゴリ別分布、しきい値変更前後の件数差分表示。
* **再導入フロー:** `apply_exclusion_asset` に入った asset を GUI から解除し、再び apply 対象へ戻す管理機能。
* **マルチモデル化:** 基本 6 ラベルと特別 2 ラベルを排他的にせず併用する。人物系は `我が子 > 家族 > 人物` の順で最上位 1 モデルだけを有効化し、それ以外の該当ラベルモデルと汎用モデルを併用する。
* **重複除外の統合:** CLIP ベクトルの近傍探索による、類似した連写画像からのベストショット選定。

構築の第一段階として、`learn` の signal 同期、`score` の全件 snapshot 保存、`apply` の Review Album 送付と重複送付抑止を優先する。
